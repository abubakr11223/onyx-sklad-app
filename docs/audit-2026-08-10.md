## 1. Fixed in this sweep

### 1.1 Cross-manager leak of client objects (the significant one)

`/klienty/[id]` and `/obekty/[id]` enforce a hard rule: a manager sees only
records whose `managerId` is their own — anything else is a 404
(`canAccessDirectoryRecord`). The sale form deliberately breaks that rule for
client **search** (`attachAnyExisting`, ТЗ №14 BUG-02) so a manager can attach an
existing card instead of creating a duplicate.

Nobody carried the rule into the **objects** of that client.
`listSitesForClient` checked only that the client existed, so the reachable path
was: search any name → receive a foreign `clientId` → list that client's sites
with names, addresses and contact persons. Two parts of the system disagreed and
the weaker one won.

Fixed by applying the same `siteListScope` the directory uses. Owner sees all;
manager sees their own. The sale still completes for a foreign client — the
object is optional, and a new one created through `createSiteForSale` belongs to
its author. Pinned by `src/tests/sale-client-scope.test.ts`.

### 1.2 Unlimited login attempts

`/login` had no attempt limit. Password storage itself is strong (PBKDF2-SHA256,
100k iterations, timing-safe, dummy-hash branch equalisation), but two things
followed from having no ceiling: passwords could be guessed indefinitely, and
**every guess cost the server 100k iterations** — making brute force a cheap way
to burn function CPU as well.

Added `LoginAttempt` (composite PK `scope` + `key`) with two scopes: `email`
(10 failures / 15 min) and `ip` (30 — one NAT can be the whole warehouse). The
check runs **before** any hashing, which is the point: rejecting after the KDF
would stop guessing but not the CPU cost. Success clears the counter; the table
prunes lazily like `TelegramWebhookReceipt`.

Deliberate trade-off: a per-email counter is itself a way to lock a colleague
out. Mitigated by a generous threshold, a short window, and immediate reset on
success — worst case for the victim is waiting out the window. The throttle
fails **open** if its own table errors: a warehouse locked out by a failure in an
auxiliary table is worse than a temporarily missing throttle.

Migration: `20260810120000_login_attempt_throttle`.

### 1.3 Dead code that silently commits half a sale

`sellAllClientSamples` had no caller and no test, and sold a client's samples one
at a time in **separate transactions**, returning an error on the Nth while the
first N−1 stayed sold. The user would read "failed"; the warehouse would hold
sold stone, debts and `SaleRecord`s. Removed, with a note on what a correct
version needs (one transaction, or partial success shown honestly in the UI).

### 1.4 Comments that describe the wrong production

`src/instrumentation.ts` stated that production runs under pm2 and therefore
"Vercel Cron never runs", and built a 15-minute in-process sweep on that basis.
`docs/deploy-vercel.md` says the opposite and is right: Vercel is live, VPS is a
spare. So the 15-minute sweep does not run at all (a serverless instance does not
outlive its request), and the real backstop is the daily `vercel.json` cron.

Correctness was never at risk — a sale re-checks expiry itself
(`isHoldEffective`) — but a reservation can read as held for up to a day in
lists. Comments corrected in `instrumentation.ts` and `reservation-cron.ts`;
README now states the deployment target plainly.

### 1.5 Lint was never run in CI

CI ran tests and build only, so 8 lint errors had accumulated unnoticed
(`react-hooks/purity`, `react-hooks/immutability`, `prefer-const`). All fixed —
the two `react-hooks` ones in `/bron` and `/prodazha` by deriving the
"nested list truncated" flag from the `map` result instead of mutating an outer
variable inside the callback. `npm run lint` is now a CI step.

Two `set-state-in-effect` errors in `SaleForm.tsx` are **suppressed on purpose**,
each with a reason at the call site. Rewriting that step into derived state would
change exactly the behaviour that was repaired twice — the error must appear on
the step where the button was pressed. That is this project's most-regressed bug
class (`tz-audit-2026-08-09.md` §4, five incidents). Change it only with a manual
sale run in a browser, never to satisfy a linter.

### 1.6 Undocumented environment variables

`ANTHROPIC_API_KEY` (broken-stone shape detection) and the Vercel Blob token were
used by code and mentioned in no `.env` example, so the features looked broken
for no visible reason. Documented — including that AI interiors do **not** use
the Anthropic key: they go through the Vercel AI Gateway
(`google/gemini-2.5-flash-image`), which needs `AI_GATEWAY_API_KEY` locally.

### 1.7 A guard for a failure only the build log reports

Exporting a plain constant from a `"use server"` module makes Next drop **every**
export from it — "The module has no exports at all" — which breaks the whole sale
form at runtime. `tsc` passes, tests pass, and `next build` still exits **0**; the
only signal is one line in the build log. This sweep hit it while fixing 1.1.

`src/tests/use-server-exports.test.ts` now fails if any action file exports
anything other than an async function or a type.

## 2. Open — needs an owner decision, not more code

### 2.1 Slab thickness cannot be recorded accurately

Since the 2026-08-07 migration all dimensions are centimetres, stored as `Int`.
Slabs are conventionally 18, 20 or 30 mm; in whole centimetres **18 mm cannot be
expressed** — 20 mm and 30 mm survive, 18 mm does not. The migration also
truncated rather than rounded (`18 / 10 = 1` in integer division), so any legacy
18 mm row became 1 cm — wrong by 44%.

The real warehouse has not been loaded yet, so the damage is limited to demo
rows. The limitation, however, is still ahead of you. Options: store thickness in
millimetres, or allow one decimal place. Both touch validators, forms, display,
search and seeds — worth doing **before** real intake, not after.

### 2.2 Инвентаризация (ТЗ §9) does not exist

`slabsAdjusted` / `areaAdjustedM2` are read everywhere and feed the remainder
formula, `AuditLog.ADJUSTMENT` is defined and labelled in `/istoriya` — and
nothing ever writes them. Batch edit changes the totals instead, which is a
different act (fixing an intake typo, not reconciling with a physical count).

ТЗ §9 calls trust in the system the project's main risk. This is the mechanism
that catches drift between the system and the shelf; it will be wanted early once
real stock is in.

### 2.3 Smaller calls

- **`/api/karta` POST** requires a real session but no role, so any signed-in
  employee can toggle cells; GET is fully open. It is the project map, not
  warehouse data — decide whether that is intended before adding a gate that
  might break the existing workflow.
- **Partial debt repayment** is not supported (`repayDebt` is full-only, stated
  in the code). Real collection usually is partial.
- **Three finished branches never merged**, most notably
  `origin/claude/tanish-5317b2` — Telegram push to the OWNER when someone
  requests access. Without it the owner learns of a request only by opening
  `/accounts`.
- **`/q/[slug]` loads a stone type's batches unbounded** to derive one neutral
  "in stock" flag, on a public unauthenticated route. Left as is on purpose: the
  bound cannot be added with a plain `take` without changing what the flag means
  (the row with stock may be the last one), and a correct fix needs the
  column-to-column comparison pushed into SQL. Low volume today; revisit if a
  stone type ever accumulates hundreds of batches.
