## 1. Две задачи этого ТЗ

1. **Обязательные размеры при приёмке.** Сейчас при приёмке заводится только количество (плиты, м²) и толщина в узорах. Габаритов плиты (длина × ширина) нет. Нужно добавить размеры и сделать их обязательными при заведении товара.
2. **Единая единица измерения — сантиметры.** Сейчас во всех размерах стоит «мм» (в разбитии, узорах, поиске, карточках боя). Нужно везде заменить на «см».

---

## ЧАСТЬ A · Обязательные размеры при приёмке

### 2. Что добавить в форму приёмки

В блок приёмки (сейчас: Вид → Количество → Узоры → Локации → Детали) добавить **размеры плиты**. Логика натурального камня: в партии плиты обычно одного формата (одна поставка = один размер плиты), но узоры/толщины внутри различаются — это уже учтено подгруппами.

**Размеры на уровне партии (обязательно):**
```
РАЗМЕР ПЛИТЫ *
Длина, см *   [ ... ]
Ширина, см *  [ ... ]
Толщина, см   [ ... ]   (если в партии одна толщина; если разные — в узорах)
```

- Длина и ширина плиты — **обязательны** при приёмке. Без них партию не принять.
- Толщина: если партия однородная — указывается здесь; если в партии несколько толщин — берётся из подгрупп узоров (там поле толщины уже есть). Не дублировать: когда включён блок «несколько узоров/толщин», толщина задаётся в узорах, а на уровне партии скрывается или становится необязательной.

**Если в партии разные размеры плит** (бывает у натурального камня): размер можно задавать на уровне подгруппы узора — добавить в таблицу узоров поля «Длина, см» и «Ширина, см» рядом с толщиной. Тогда:
- Однородная партия (галочка узоров не стоит) — размер один, на уровне партии, обязателен.
- Партия с подгруппами — размер задаётся по подгруппам (длина/ширина/толщина в каждой), обязателен в каждой подгруппе.

### 3. Зачем это нужно (обоснование)

- Поиск по размеру (сценарий 6.5 основного ТЗ) работает по габаритам. Если у плит партии нет размеров — целые плиты не находятся по размеру, только бой/остатки. Сейчас поиск по целым плитам неполноценный.
- B2C-клиенту важен размер плиты (столешница, облицовка). Менеджер должен видеть габарит, не гоняя складчика.
- Площадь можно проверять/считать из размеров (длина × ширина × кол-во плит), а не вводить вручную с ошибками.

### 4. Проверки

- Приёмку нельзя завершить без длины и ширины (обязательные поля).
- Для партии с узорами размеры берутся из подгрупп, обязательны в каждой.
- Размер плиты виден в карточке камня, в поиске, в продаже.
- (Желательно) при вводе размеров и количества плит — автопроверка площади: длина × ширина × плиты ≈ введённая площадь; при сильном расхождении — подсветить.

## ЧАСТЬ B · Перевод всех размеров мм → см

### 5. Единое требование

Везде, где сейчас размеры в миллиметрах (мм), заменить на сантиметры (см). Единица измерения по всей системе — **сантиметры**. Площадь остаётся в м², количество — в плитах.

### 6. Где именно менять (полный список мест)

Проверено по live-версии. Заменить «мм» → «см» во всех этих местах:

1. **Приёмка** — «Толщина, мм» в подгруппах узоров → «Толщина, см». Плюс новые поля размеров из части A — сразу в см.
2. **Разбить** (`/razbit`) — четыре поля:
   - «Стороны, мм (необязательно)» → «Стороны, см».
   - «Длина, мм *» → «Длина, см *».
   - «Ширина, мм *» → «Ширина, см *».
   - «Толщина, мм» → «Толщина, см».
   - Подсказки/плейсхолдеры (примеры вида «1180, 640, 950») пересчитать в см: «118, 64, 95».
3. **Бой по фото** (форма размеров из Telegram-бота) — размеры сторон тоже в см.
4. **Поиск** (`/poisk`) — «Нужный размер (мм)», поля длина/ширина, «запас на рез 20 мм» → всё в см (запас на рез «2 см»).
5. **Карточки боя/остатка** — вывод «Габарит 1180×640 мм» → «Габарит 118×64 см». Везде, где габарит показывается (поиск, продажа, должники, образцы).
6. **Должники / Образцы / Продажа** — где показываются габариты боя/остатка, тоже см.

### 7. Важно: пересчёт данных, а не только подписи

Это ключевой момент — **не просто заменить текст «мм» на «см», а пересчитать значения**:

- Существующие данные в базе (габариты боя, размеры) хранятся в мм. При переходе на см их нужно либо пересчитать (разделить на 10), либо хранить как есть, а на экране делить на 10. Определиться с подходом, но результат: пользователь везде видит корректные сантиметры.
- Пример: бой «1180×640 мм» должен показываться как «118×64 см», а не «1180×640 см» (это была бы ошибка в 10 раз).
- Ввод: когда пользователь вводит «118» в поле «Длина, см» — система понимает это как 118 см. Внутреннее хранение — на усмотрение разработчика, но ввод/вывод в см и без ошибок масштаба.

### 8. Проверки

- Во всех перечисленных местах (п.6) единица — «см», «мм» не осталось нигде.
- Старые записи боя/остатков показывают корректный размер в см (118×64, а не 1180×640).
- Ввод размера в см сохраняется и отображается верно; поиск по размеру в см находит подходящий камень.
- Плейсхолдеры и подсказки пересчитаны в см.
- Запас на рез отображается в см.

## 9. Приоритет и порядок

**Приоритет: High.**
- Часть B (мм → см) — простая, но требует аккуратного пересчёта данных, не только подписей. Сделать внимательно, чтобы не было ошибки масштаба ×10.
- Часть A (обязательные размеры при приёмке) — закрывает реальную дыру: без размеров плит поиск по целым плитам не работает.

**Порядок:**
1. Часть B — перевод мм → см с пересчётом (быстро, но аккуратно).
2. Часть A — размеры при приёмке (уже сразу в см).

**Зависимость:** Critical-баги из ТЗ №7 (если ещё остались) — вперёд. В остальном независимо.
