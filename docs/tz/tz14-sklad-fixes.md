## 0. Контекст

Показывали платформу на складе, вскрылись три проблемы. Провёл живую диагностику каждой — ниже причины (не догадки) и что исправить. Две первые — баги (сломано то, что должно работать), третья — недостающая функция.

## 1. BUG-01 (Critical) · Образец не появляется в разделе «Образцы»

**Симптом (со склада):** образец выдаётся в разделе «Продажа», но в разделе «Образцы» не появляется.

**Что показала диагностика:** раздел «Образцы» полностью пуст — 0 активных, 0 закрытых, ни одной записи. То есть выданный образец **вообще никуда не записался**, а не «попал не в ту вкладку».

**Вероятная причина (для разработчика):** действие «Выдать как образец» в форме продажи не создаёт запись образца в базе — либо submit не доходит (как были прошлые баги с формами, ТЗ №4/№5), либо образец пишется со статусом/типом, который раздел не читает. Нужно проверить:
- Реально ли «Выдать как образец» отправляет данные на сервер (а не молча завершается).
- Создаётся ли запись образца и с каким статусом.
- Фильтрует ли раздел «Образцы» по статусу так, что активный образец выпадает.

**Что должно быть (напоминание из ТЗ №10):** выдал образец → камень списан со статусом «на руках у клиента» → образец сразу виден в «Активные» с клиентом, камнем, сроком, залогом, менеджером.

**Проверка после фикса:** выдать образец в продаже → он появляется в «Образцы → Активные» немедленно; «Вернули» → камень назад в наличие; «Оформить продажу» → образец в «Закрытые».

## 2. BUG-02 (High) · Поиск клиента в продаже не находит по имени

**Симптом (со склада):** при оформлении продажи поиск существующего клиента по имени не выдаёт результат; по номеру телефона — находит.

**Что показала диагностика (важное уточнение):** в справочнике «Клиенты» (`/klienty`) поиск по имени работает гибко — находит по полному имени, частичному («Тим»), середине слова, с пробелом. То есть **проблема не в данных и не в общем поиске, а именно в форме продажи** — там используется отдельный, более строгий механизм поиска клиента, который по имени не срабатывает, а по цифрам номера — да.

**Вероятная причина (для разработчика):**
- В форме продажи поиск клиента идёт по другому запросу, чем в справочнике (например, точное совпадение вместо «содержит», или ищет только по полю телефона, а имя игнорирует).
- Возможна чувствительность к регистру / раскладке (кириллица «Тимур» vs латиница «Timur» — латиницу не находит даже справочник).

**Что нужно:**
- Поиск клиента в продаже должен работать так же, как в справочнике «Клиенты»: по имени И по телефону, по частичному совпадению, без учёта регистра, устойчиво к пробелам.
- Использовать один и тот же механизм поиска клиента в обоих местах (продажа и справочник) — чтобы не было двух разных поведений. Это и надёжнее, и проще поддерживать.
- Желательно: показывать выпадающий список совпадений по мере ввода (и по имени, и по телефону), чтобы менеджер сразу видел клиента.

**Проверка после фикса:** в продаже ввести часть имени существующего клиента → он находится; ввести телефон → находится; регистр и лишний пробел не мешают.

## 3. Новая функция (High) · Редактирование добавленной партии

**Запрос (со склада):** складчик завёл партию и хочет исправить ошибку в количестве и размерах.

**Что показала диагностика:** редактирования партии нет вообще — приёмка только создаёт новую партию, списка партий с возможностью изменить нет. Ошибку сейчас исправить невозможно (только заводить заново, что путает учёт).

### 3.1. Что нужно

Дать возможность редактировать уже созданную партию: количество, размеры, узоры/подгруппы, локации, детали (дата, поставщик).

**Где:** список партий с кнопкой «Редактировать» у каждой. Логичные места — раздел приёмки (вкладка/подраздел «Партии») или карточка партии из поиска. Предлагаю: в приёмке добавить список «Ранее принятые партии» с поиском и кнопкой «Редактировать».

**Что можно редактировать:**
- Количество (плиты, м²).
- Размеры плиты (длина, ширина, толщина — в см, по ТЗ №12).
- Узоры/подгруппы (описание, толщина, количество, фото).
- Локации (блок, ориентир, распределение).
- Детали (дата прихода, поставщик/документ).

### 3.2. Правила и защита (доработка до идеала)

Простое редактирование опасно — партия могла уже частично участвовать в продажах/брони/бое. Поэтому:

- **Если по партии уже были движения** (продажи, брони, бой/остатки из неё) — редактировать количество можно, но система должна предупредить и не дать увести остаток в минус. Нельзя выставить количество меньше, чем уже продано/забронировано.
- **Свободное редактирование** (нет движений по партии) — меняется всё без ограничений.
- **Размеры и детали** (длина, ширина, поставщик, дата) — можно править всегда, это не влияет на остаток.
- **Журнал:** каждое редактирование пишется в Историю — кто, что изменил, старое → новое значение. Это защита от злоупотреблений (важно: изменение количества/цены — чувствительная операция).
- **Доступ:** кто может редактировать — уточнить у Onyx. Предлагаю: складчик правит свои недавние партии (например, в течение суток), дальше — только владелец/менеджер. Или сразу: правки количества — владелец, правки размеров/деталей — складчик. Согласовать.

### 3.3. Проверка после реализации

1. Партию можно открыть на редактирование из списка.
2. Количество, размеры, узоры, локации, детали меняются и сохраняются.
3. Нельзя уменьшить количество ниже уже проданного/забронированного — система предупреждает.
4. Изменение пишется в Историю (кто, что, было → стало).
5. После правки поиск/продажа/карта показывают обновлённые данные (синхронно).

## 4. Приоритет и порядок

**Critical:**
1. BUG-01 — образец не сохраняется/не отображается. Раздел выдан клиенту как рабочий, а он не работает — критично для доверия к системе.

**High:**
2. BUG-02 — поиск клиента в продаже по имени.
3. Редактирование партии (с защитой по остаткам и журналом).

**Порядок:** сначала два бага (быстро, ломают уже показанный функционал), затем редактирование партии.

**Связь:** редактирование размеров партии делать с учётом перехода на см (ТЗ №12). Поиск клиента — переиспользовать механизм из справочника (ТЗ №11), не писать третий.

---

## 5. Общее наблюдение

Две из трёх проблем (образец, поиск клиента) — это разделы, которые в прошлых проверках числились «реализованными по структуре», но на реальном использовании выявились скрытые баги: образец не пишется, поиск в продаже отличается от справочника. Рекомендую при сдаче каждого раздела прогонять **полный сквозной сценарий на реальных данных** (выдал образец → проверил в разделе; нашёл клиента по имени в самой продаже), а не только проверять, что раздел открывается. Это ловит такие баги до показа на складе.
